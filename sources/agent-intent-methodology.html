Agent 意图判断与连续执行方法论

好用的 Agent 不靠”模型特别聪明”猜意图，靠的是一条工程化流水线，把模糊问题逐步变成明确动作：

输入归一化 → 显式路由 → 上下文补全 → 能力约束 → 模型分工 → 工具事件循环 → 分层反馈 → 可恢复收尾

核心认知：不要让模型同时做 4 件事

很多系统失败，是因为把四件事全丢给一个模型：理解意图、决定是否调工具、选工具、组织回复。

正确做法是拆层：

层职责
规则层处理高确定性的东西（命令路由）
上下文层补足模型缺失的事实
策略层收紧可行动作空间
模型层只负责剩余的模糊决策
执行层工具调用变成可追踪事件流
反馈层过程和结果拆开表达

原则一：高置信意图先用规则

这些意图不该交给模型猜：以 / 开头的显式命令、明确的模式切换、已知关键字触发的预定义流程。

模型不用先猜”你是不是想 review”，而是直接进入”如何 review”。

原则二：先补事实，再让模型决策

模型判断不准，很多时候不是智力问题，而是事实缺失。建议至少注入四类上下文：

  1. 运行时上下文：当前目录、日期、模式
  2. 项目上下文：规范、约定、git 状态
  3. 用户上下文：偏好、语言、输出风格
  4. 执行上下文：可用工具、权限模式、已执行动作

不要把事实藏在代码里让模型自己猜。要显式注入。

原则三：给”本轮能力包”而非全部能力

能力包 = 当前轮次允许的工具集合 + 权限集合 + 可写路径 + 风险上限。

场景允许工具风险
解释报错Read, Grep, Globlow
修复测试Read, Grep, Edit, Bashmedium
发版部署Read, Bash, Git（需确认）high

不是问”模型，你觉得应该做什么”，而是问”在这个能力包里，你最合理的下一步是什么”。

原则四：按阶段分工模型

角色职责
主执行模型理解任务、制定下一步、调用工具、整合结果
审查模型challenge 主模型、提前纠偏、完工前复核
摘要模型压缩工具结果、进度摘要
回退模型主模型不可用时接管

简单选择策略：短任务用单主模型，高风险任务加审查模型，高负载场景加 fallback。

原则五：微回合循环

好的 Agent 不是一次输出到底，而是不断重复：推理 → 工具 → 结果 → 再推理。

每一步都建立在新证据上，不是先假设一整条路径。错误不会一路放大。

原则六：区分可并发与不可并发工具

类型执行方式示例
只读批量并发Read, Grep, Glob
有副作用串行，每步后刷新上下文Edit, Write, Bash

原则七：权限是策略引擎

权限系统输出三类结果：allow / ask / deny。

判定顺序：deny 规则 → ask 规则 → 工具安全检查 → 模式放行 → allow 规则 → 人工确认。

危险动作不能只靠模型自觉。必须在模型外有一层策略裁决。

原则八：反馈分层

层内容
初始化反馈当前位置、可用能力、当前模式
进度反馈正在读文件、正在搜索
结构性反馈已切换模型、某步被权限阻止
最终反馈结论、修改内容、验证结果、风险与下一步

原则九：隐式补全要克制

适合补的：相关 memory、项目规则、近期工具结果、IDE 选区。

不该补的：主观需求猜测、自动扩大行动范围、追加高风险操作。

最小可复现版本

7 条落地规则

  1. 显式命令优先于自然语言理解
  2. 所有高风险动作都要经过策略层
  3. 每轮只暴露必要工具
  4. 推理拆成多轮工具回路
  5. 上下文要显式注入
  6. 进度反馈、结构反馈、最终反馈分开
  7. 中断、fallback、恢复当主路径设计

反模式

  • 全量工具列表直接塞给模型
  • 没有规则路由，所有请求走大模型
  • 没有能力约束
  • 一个模型同时做执行、审查、摘要
  • 没有中间反馈
  • 工具结果不回填上下文
  • 没有恢复机制

最终抽象

先用系统把任务空间压缩，再让模型在一个受控、带上下文、可恢复的局部空间里做决策。

这比”训练一个更聪明的模型”更重要，也更容易工程落地。
