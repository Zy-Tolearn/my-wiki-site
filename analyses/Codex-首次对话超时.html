五、完全退出 Codex，再重新打开

这是最容易漏掉的一步。

设置 Windows 用户级环境变量后，已经运行中的 Codex 进程不会自动拿到新值。必须完全退出 Codex，再重新打开，让新进程重新继承环境变量。

只新开一个对话通常不够。

推荐顺序：

  1. 完全退出 Codex。
  2. 确认 Clash Verge 已启动，并且 7897 是 mixed/http 代理端口。
  3. 重新打开 Codex。
  4. 再发起第一次对话测试。

如果还是 reconnecting，可以再试一次：先退出 Codex 和 Clash Verge，然后先开 Clash，再开 Codex。

七、为什么 .env 更适合 Codex

.env 的好处是只影响 Codex，不会把代理设置扩散到整个 Windows 用户环境。对“只有 Codex 第一次对话超时”的情况，这个落点更干净，也更容易迁移和撤销。

用户级环境变量适合需要让很多命令行工具都走同一个代理的情况；.codex/.env 更适合只修 Codex 自己。

八、为什么用户级环境变量也有效

这个问题的根因是 Codex 作为桌面应用启动时，会从 Windows 用户环境继承网络代理设置。临时在某个 PowerShell 窗口里设置 Process 级变量，只对当前 PowerShell 进程有效，不一定影响已经启动或由桌面启动器启动的 Codex。

所以更稳的落点是 Windows 用户级环境变量：

换句话说，修复的关键不是“在当前命令行里能不能访问代理”，而是“Codex 这个进程启动时有没有继承代理变量”。

九、排障清单

检查项判断
Clash 是否启动`netstat -ano
端口是否正确Clash Verge 中确认代理端口，默认常见为 7890，改过则以实际端口为准
Codex .env 是否写入C:\Users\<用户名>\.codex\.env 中有 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY
用户级变量是否写入如果使用备用方案，GetEnvironmentVariable('HTTPS_PROXY','User') 返回代理地址
Codex 是否重启必须完全退出再打开
本地地址是否直连NO_PROXY=localhost,127.0.0.1,::1

结论

Codex 第一次对话 reconnecting、超时，不一定是模型或账号问题。对 Windows + Clash Verge 用户来说，先检查 Codex 是否继承了代理环境变量，往往比反复重试更有效。

现在更推荐的最终方案是：在 C:\Users\<用户名>\.codex\.env 里写入 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY 和 NO_PROXY，统一指向 Clash 的本机代理端口：

如果你的 Clash 端口不是 7890，就换成自己的端口，例如 7897。然后按“先 Clash，后 Codex”的顺序重启。这个方案的核心只有一句话：让 Codex 进程启动时就带着正确的代理设置。
